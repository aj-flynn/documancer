# Source data contract · schemaVersion 2

All content strings are plain text, escaped by the renderer. No Markdown parsing or raw HTML. The only content that does not come from a JSON string is a file beside the source: an image, or a preview prototype (see "Files beside the source"). UTF-8 JSON is the editable source of truth. Unknown properties are rejected so typos do not silently drop content.

Required top-level fields:

- `schemaVersion`: `2`. The renderer rejects any other value; a document written for an earlier version must be brought up to this contract first (see the end of this file).
- `mode`: `technical`, `user-guide`, `uat` or `preview`.
- `title`, `lead`: nonempty strings.
- `identity`: object with nonempty `id`, `version`, `date` (valid YYYY-MM-DD) and `source` (code/release identity or explicit uncertainty). Optional strings: `repositoryRoot`, `branch`, `commit`, `readiness`.
- `overview`: nonempty block array. It follows the title and lead directly, with no heading, and is the first thing a reader sees: keep it to what they need before starting. In UAT the renderer adds a linked list of the tests with their current results beneath it.

Identity is shown in the page footer and included in the UAT summary; it does not appear at the top of the document. `identity.source` is recorded in the JSON and the UAT summary but is not displayed in the footer.

Optional shared fields:

- `brand`: `{ "name": "Publisher", "logo": "none" }`. Name defaults to Flynn Technology LLC; logo is `flynn` or `none`. If name is customized and logo omitted, text branding is used. Explicit `flynn` requires the Flynn company name.
- `context`: optional `{ "summary", "links" }`, shown as an "At a glance" panel beside the document, and under the lead on narrow screens and in print. Supply either or both. `summary` is at most 280 characters and must not repeat the lead. `links` is a nonempty array of `{ "kind", "label", "href" }`; `kind` is a short free-text label such as Ticket, Pull request, Repository or Design doc. Web links open in a new tab. Omit `context` when there is nothing real to put in it; never invent a ticket or link.
- `generatedBy`: optional `{ "agent", "model" }` naming the tool and model that wrote the document, for example `{ "agent": "Claude Code", "model": "Claude Sonnet 5.5" }`. Supply either or both. It is shown in the footer as "Generated by" and included in the UAT summary. Record only what you actually know about the session you are running in; omit a value you would have to guess, and omit the field for a document written by a person.
- `related`: optional legacy label overrides (`{ "label", "href" }`) for matching companions in an explicitly generated set. It does not create links to files outside that set. Omit for automatic guide labels. Standalone exports ignore this field for navigation.
- `sources`: array of `{ "label", "href" }` source links. They appear in Overview, keeping Summary last for UAT.

Technical and user-guide modes require `sections`: nonempty array of `{ "id", "title", "blocks" }`. Section IDs are unique lowercase slugs beginning with a letter (`[a-z][a-z0-9-]*`). `overview` is reserved. Do not supply UAT fields in these modes.

Preview mode has its own fields (`ticket`, `problem`, `findings`, `impact`, `questions`, `views`, `work`, `leaveAsIs`), defined in [preview.md](preview.md). They are rejected in every other mode, and preview rejects `sections`, `setup`, `tests`, `evidence` and `related`.

UAT requires `setup` (nonempty block array) and `tests` (nonempty array). Do not supply `sections`. Optional `evidence` is an array; omit it if unavailable.

Each UAT test requires:

```json
{
  "id": "UAT-01",
  "title": "Find a topic",
  "brief": "Judge whether the matching topic is easy to locate.",
  "prerequisites": [{ "type": "paragraph", "text": "Use the user guide. Search text: appearance." }],
  "steps": ["Type appearance in Find in this document.", "Choose the matching topic."],
  "expected": "The selected topic is visible.",
  "problemSigns": "A missing match or a link to the wrong section.",
  "reset": "Clear the search field.",
  "rehearsal": "Not rehearsed; the target application was unavailable."
}
```

Test IDs begin with a letter and contain letters, digits or hyphens. IDs must be unique, case-insensitively. Result and notes are intentionally not accepted in source data; new documents always start Untested. Evidence records require `title`, `status` (`passed`, `failed`, `blocked`, `untested`), `detail`; optional `history` is a nonempty string. Include execution date, command/check, tested code/configuration/data and meaningful observations in `detail`.

## Content blocks

| Type | Fields |

### Diagrams

Use diagrams when relationships, branches, sequence or state changes are easier to understand visually. All text is escaped, including SVG labels. No raw SVG, HTML, Mermaid, external images or network resources are accepted. The generated SVG uses the document's embedded font and theme colors, and remains visible without JavaScript. A keyboard-focusable horizontal scroll region preserves the diagram's readable size on narrow screens. With JavaScript and browser dialog support, clicking the SVG, pressing Enter in its scroll region, or selecting Expand diagram opens a full-window modal with scrolling, a Close diagram button and Escape support. Closing restores focus to the opener. No browser fullscreen permission is needed. Without JavaScript or dialog support, the static diagram and text alternative remain usable and expansion buttons stay hidden. A text alternative lists every node and directed relationship; the author supplies the explanatory `description`.

```json
{
  "type": "diagram",
  "caption": "Document generation",
  "description": "Source JSON is validated before HTML is written. Invalid input must be corrected before trying again.",
  "nodes": [
    { "id": "source", "label": "Editable JSON" },
    { "id": "validate", "label": "Validate source" },
    { "id": "html", "label": "Self-contained HTML" },
    { "id": "fix", "label": "Correct source" }
  ],
  "edges": [
    { "from": "source", "to": "validate" },
    { "from": "validate", "to": "html", "label": "Valid" },
    { "from": "validate", "to": "fix", "label": "Invalid" },
    { "from": "fix", "to": "source", "label": "Retry" }
  ]
}
```

Each diagram has 1–40 nodes and 0–80 directed edges. Each node requires a unique lowercase-slug `id` and a nonempty `label` of at most 180 Unicode code points. IDs are local to the diagram. Optional `direction` is `down` or `right`. Without it, the renderer tries both: it keeps the one with fewer crossings, and on a tie the one that fits the text column (about 800 pixels) without scrolling sideways, since a tall diagram scrolls with the page; otherwise top to bottom. Leave out `row` and `column` and the renderer places every node itself (see below). To place nodes by hand instead, give every node integer `row` and `column` positions from 0 to 15; positions start at the top left, two nodes cannot occupy one cell, and a diagram cannot mix placed and unplaced nodes. Each edge requires existing `from`/`to` node IDs and an optional nonempty `label` of at most 48 code points. Duplicate directed edges and self edges are rejected; reverse edges and cycles between different nodes are supported. Unknown fields are rejected.

A node or an edge may carry an optional `change`: `added`, `removed` or `changed`. It marks what a proposal alters, in any mode. The mark is drawn with colour, line style and a text tag (a tag above a node, the word in brackets on an edge label), and is repeated in the text alternative. Leave `change` off everything that stays as it is.

#### Laying out a diagram

Leave out `row` and `column` and let the renderer lay the diagram out. It uses a layered layout, the method of Graphviz `dot`: every arrow points in the diagram's `direction` except those that close a loop, such as a retry; each node goes in the layer after the nodes that point to it, moved toward the side where most of its edges go; each layer is ordered to cut crossings; and nodes line up under the nodes they connect to. It tries a few arrangements and keeps the one with the fewest crossings, then the smallest area. Every edge is drawn; none is ever dropped. Set `direction` only to force one: `right` suits a long chain such as a pipeline that would otherwise be very tall. Place nodes by hand only when the reading order matters more than short arrows, for example to match a screen or a familiar picture, and then follow rules 2 and 3 yourself.

1. **Decide first whether a diagram is the right form.** A diagram suits a flow, a branch, a lifecycle, or a few components and how they connect. A many-to-many relationship such as "which project references which" is clearer as a table with one row per item and a column listing what it depends on. Use a diagram for that only when it is small, or to show one item's dependencies.
2. **Pick one direction of flow** and keep every arrow pointing that way. For dependencies, the things that use others go first and the foundations last. An arrow against the flow is right only when it closes a loop.
3. **Put connected nodes next to each other**: each node in the row (or column) after the nodes that point to it, under or beside the nodes it connects to, so arrows run short and straight.
4. **Keep it small.** Aim for at most 12 nodes, no more than about 1.5 edges per node, and no node with more than 5 edges. A node with many edges deserves a diagram of its own; a dense system deserves several focused diagrams. Split a diagram rather than leaving edges out: a diagram that omits real relationships misleads.
5. **Connect every node.** A box with no arrows says nothing about how it fits; describe it in prose instead.
6. **Label every branch** leaving a decision, keep labels short, and explain detail in the description or nearby prose.

The renderer routes orthogonal arrows around boxes. Each edge leaves and enters a box at its own point and never shares a line with another edge; where two edges must cross, the horizontal one hops over the vertical one. When the gaps between boxes are too crowded, the renderer widens them and routes again. A diagram in which some edge still cannot be drawn on lines of its own, usually because one box has more edges than its sides have room for, is rejected with the path of that edge: give that node fewer edges or split the diagram. Grid placement carries no meaning by itself, so author every intended arrow explicitly. This is a box-and-arrow vocabulary, not UML or a sequence-diagram grammar.

#### Splitting a diagram

Split a diagram when it gives any of these warnings: crossings remaining after automatic layout, more than 12 nodes, more than 1.5 edges per node, or a node with more than 5 edges that is not the subject of the diagram. Also split it when readers will come with different questions, such as "what does the API use?" and "what does the data layer depend on?". A dense diagram answers neither.

Never split by leaving edges out. Cut along a seam the reader already understands:

- **By consumer.** One diagram per top-level item, showing what it uses: a project and its references, a service and its calls. A diagram about one node may give that node any number of edges.
- **By layer.** Applications to libraries in one diagram, libraries to shared foundations in another.
- **By path.** The main path of a flow or lifecycle in one diagram, and failure, cancellation or recovery paths in another.
- **By subsystem.** One diagram per area, plus a small overview with one box per area and an arrow wherever any edge crosses between them.

Then check:

1. **Every edge appears in at least one diagram.** Count them: the edges in the parts must add up to at least the edges of the whole. A node may appear in several parts.
2. **Each part passes on its own**, with no warnings left unexplained.
3. **Each caption names its slice**, such as "What the API references", and each description says where the rest is.
4. **The parts are introduced together**, in one section or a `details` block, and in an order that tells the reader where to start.

When no seam gives parts that pass, use a table instead: one row per item, and a column listing what it connects to.

For example, a diagram of eleven projects and 25 references drawn as one diagram keeps 14 crossings, and four projects have six or more edges. Split by consumer, it becomes four clean diagrams that cover all 25 references once each: what the API references (8), what the job references (6), what the PA site references (4), and what the libraries reference (7).

`render.mjs` and `render.mjs --check` print a warning to standard error, with the path of the diagram, when a diagram breaks rules 2 to 5: edge crossings, an arrow against the flow that is not a loop back, more than 12 nodes, more than 1.5 edges per node, a node with more than 5 edges unless the diagram is about that node, or a node with no edges. Warnings do not stop the render. Resolve them, or be ready to say why a warning is acceptable for that diagram.

Diagrams work anywhere blocks are accepted, including nested details and UAT prerequisites. Verify the final HTML in both themes and at narrow widths: readable labels, correct arrow directions, no clipping or ambiguous overlaps, keyboard scrolling, and no page-wide horizontal overflow. Successful CLI rendering alone is not visual verification.

### Images and files beside the source

An `image` block embeds a local file in the HTML as a data URI, in any mode. Use it for a screenshot the text needs; do not use it for decoration or for anything a diagram block can draw. `file` is a path relative to the folder holding the source JSON, with forward slashes. It may not be absolute, contain `..`, or name a file outside that folder, and remote images are not accepted. The file must be a PNG, JPEG or WebP of at most 1 MB whose content matches its extension; all files in one document may total at most 6 MB. `alt` is required and says what the image shows. With JavaScript, clicking the image or Expand image opens it in the same full-window dialog as a diagram.

Because files are read at render time, a document that refers to one must be rendered from its source file (the CLI does this) or with `baseDirectory` passed to `renderDocument`. `node scripts/render.mjs --check source.json` validates a source and its files without writing anything.

Links support HTTPS, HTTP, mailto, fragment anchors and relative document paths. Protocol-relative URLs, backslashes, control characters and other schemes are rejected. Local fragment links must reference a generated section ID; cross-document fragments are the author's responsibility. The renderer never fetches linked resources.

The CLI validates required fields, object keys, dates, modes, URL schemes, table widths, ID uniqueness and referenced files. It cannot verify product claims, source freshness or remote link reachability. No generated timestamp enters the document build, so the same source and package produce the same HTML. UAT summaries receive their own generation time when the user clicks Generate summary.

## Generating a document set

Use `node scripts/render.mjs --set set.json output-directory`. The manifest has one `documents` array; each entry has `source` (JSON path relative to the manifest) and `output` (relative HTML path within the output directory). Include at most one document of each mode. A preview cannot be in a set; render it on its own. See `../examples/set.json`. All sources are validated and rendered before output is written. Duplicate outputs, duplicate modes and traversal paths are rejected.

Header links come only from the current set, regardless of stale files in the destination. Technical and user guides link only to each other; UAT is excluded. UAT links to either guide open in a new tab with `noopener noreferrer` and an accessible new-tab announcement. Known companion links in body blocks and sources follow the same UAT policy. Do not author links to other UAT files in public documentation. Single-document CLI rendering has no companion navigation.

This is a build-time distribution boundary, not a runtime file probe. If the distribution subset changes, render that subset again; existing HTML cannot detect a guide deleted or withheld after generation. Source links and ordinary content links are still authored links, not availability-checked companion navigation.

## Updating a schemaVersion 1 document

Set `schemaVersion` to `2`. No field was removed or renamed. Version 2 adds the optional `context` and `generatedBy` fields and reserves the section ID `document-content`; rename a section that uses it. Then render again and fix anything the renderer reports.

## Added since schemaVersion 2 was introduced

These additions need no change to an existing version 2 document. Package 1.6.0 added `mode: "preview"` with its fields, the `image` block, and the optional `change` field on diagram nodes and edges. Five more IDs are reserved in preview mode only: `problem`, `findings`, `impact`, `work` and `decision`. Package 1.8.0 made diagram `row` and `column` optional, so the renderer lays out a diagram that omits them, added the optional `direction`, and raised the highest row and column to 15.
